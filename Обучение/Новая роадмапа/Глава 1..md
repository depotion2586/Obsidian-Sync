## Подглава 1.1: Архитектура современных приложений

_Цель: Понять, как код превращается в работающие сервисы, и какие типы архитектур придется обслуживать._

- **Жизненный цикл разработки ПО (SDLC):** Фазы (Plan, Code, Build, Test, Release, Deploy, Operate, Monitor). Место DevOps в SDLC. Agile vs Waterfall.
    
- **Анатомия Frontend'а:**
    
    - Статика (HTML/CSS/JS) vs Server-Side Rendering (SSR) vs Single Page Application (SPA).
        
    - Где это хостится: CDN, S3-совместимые хранилища, Web-серверы (Nginx/Apache).
        
- **Анатомия Backend'а:**
    
    - Web-сервер (Nginx) -> Application-сервер (Gunicorn, uWSGI, PM2, Tomcat) -> Исполняемый код.
        
    - Stateful vs Stateless приложения (почему Stateless критичен для масштабирования).
        
- **Монолит vs Микросервисы:** Плюсы, минусы, сложности деплоя и сетевого взаимодействия для каждого подхода.
    

## Подглава 1.2: Взаимодействие компонентов (3L и 7L)

_Цель: Применить твои знания сетей к уровню приложения._

- **HTTP/HTTPS под микроскопом:** Методы (GET, POST, PUT, PATCH, DELETE), статус-коды (разница между 401 и 403, 502 и 504), заголовки (Headers).
    
- **Архитектура API:** * REST (Representational State Transfer) — принципы и ограничения.
    
    - Краткий обзор альтернатив: GraphQL, gRPC (поверх HTTP/2).
        
- **Сетевые преграды между Front и Back:**
    
    - CORS (Cross-Origin Resource Sharing): Что это, почему возникает ошибка, как правильно настраивать заголовки на Backend/Nginx.
        
    - Reverse Proxy (Обратный прокси): Роль Nginx/HAProxy перед Backend-приложением.
        
    - TLS-терминация: Где и как расшифровывается трафик (связь с твоим знанием TLS).
        

## Подглава 1.3: Git под капотом и продвинутые операции

_Цель: Перестать бояться сломанных репозиториев и научиться решать любые конфликты (Middle уровень)._

- **Внутреннее устройство Git (The `.git` directory):**
    
    - Как Git хранит данные: Blobs, Trees, Commits, References (указатели HEAD, ветки, теги).
        
    - Разница между Working Directory, Staging Area (Index) и Repository.
        
- **Повседневные и продвинутые команды:**
    
    - База: `clone`, `add`, `commit`, `push`, `pull`, `fetch`, `checkout`/`switch`.
        
    - Манипуляция историей: `rebase` vs `merge` (в чем разница на уровне графа коммитов).
        
    - Интерактивный rebase (`rebase -i`): склеивание (squash), изменение сообщений коммитов, удаление случайных файлов из истории.
        
    - Спасательные операции: `reflog` (как вернуть удаленную ветку), `cherry-pick`, `revert` vs `reset` (`--soft`, `--mixed`, `--hard`).
        
    - Поиск багов: Использование `git bisect`.
        
- **Решение конфликтов (Merge Conflicts):** Алгоритм действий, использование утилит (kdiff3, vscode merge conflict resolution).
    

## Подглава 1.4: Стратегии ветвления (Branching Strategies)

_Цель: Понимать, как организовать работу команды из 5, 50 или 500 человек._

- **GitFlow:** * Полная структура (`master`, `develop`, `feature`, `release`, `hotfix`).
    
    - Почему GitFlow устаревает для современных облачных CI/CD (плюсы и минусы).
        
- **Trunk-based Development (TBD):**
    
    - Разработка в одну ветку (`main`/`trunk`).
        
    - Feature Flags (Feature Toggles) как замена долгоживущим веткам.
        
    - Почему TBD — это стандарт для настоящего Continuous Integration.
        
- **GitHub Flow / GitLab Flow:** Промежуточные и самые популярные варианты для продуктовых команд.
    
- **Семантическое версионирование (SemVer 2.0.0):** Правила нумерации релизов (MAJOR.MINOR.PATCH) и тегирование в Git (`git tag`).
    

## Подглава 1.5: Enterprise использование GitHub / GitLab

_Цель: Научиться администрировать платформы хостинга кода, а не просто пушить туда код._

- **Аутентификация и безопасность:** SSH-ключи vs Personal Access Tokens (PAT). Настройка GPG-подписей для коммитов.
    
- **Pull/Merge Requests (PR/MR):** * Жизненный цикл PR.
    
    - Code Review: роль разработчика и роль DevOps (проверка тестов, безопасности).
        
- **Защита репозитория (Branch Protection Rules):**
    
    - Запрет на force-push в `main`.
        
    - Требование обязательного Code Review (аппрувы).
        
    - Требование успешного прохождения CI-пайплайнов (Status Checks) перед мерджем.
        
- **Codeowners:** Настройка файла `CODEOWNERS` для автоматического назначения ревьюеров на специфичные директории (например, `/infrastructure`).
    
- **Webhooks:** Как GitLab/GitHub сообщает CI/CD серверу о том, что произошел push или открыт PR (базовая механика интеграции).

_Цель: Внедрить проверки кода до того, как он попадет в удаленный репозиторий или сервер._

- **Введение в Server-side проверки:** * Понимание того, как локальные проверки дублируются на стороне GitLab/GitHub Actions (вводная в следующую главу про CI/CD).
