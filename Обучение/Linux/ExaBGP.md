**Определение** - ExaBGP это программа на языке Python, которая умеет только одно -> общаться по протоколу BGP.  Главная задача данной программы: взять текстовый файл или скрипт и превратить его в реальные BGP анонсы, выплюнув их в сеть и наоборот - получить анонсы BGP и превратить их в текстовый файл/передать в скрипт. Важные факты об ExaBGP:
 - Не модифицирует таблицу маршрутизации ядра
 - Не пересылает пакеты
### Примеры использования
1. Защита от DDOS атак
	Скрипт мониторит нагрузку через FastNetMon или sFlow. Видит аномалию согласно написанному условию - отправляет на пиринги анонс IP злоумышленика/ов с определенным комьюнити что бы аплинк еще на своих сетях дропал пакеты вредоноса
2.  Построение отказоустойчивых сервисов
	Скрипт проверяет находясь на сервере приложения насколько загружены серверы, связанные между собой BGP/это может быть и балансировщик. Если нагрузка критическая или сервер упал - скрипт срабатывает и перестает анансировать свой IP вышестоящему серверу или балансировщику и находится другой маршрут
3. Инжекция маршрутов 
	Ведет себя как настоящий роутер и может симулировать анонсы маршрутов, заранее записанные в текстовый файл

### Взаимодействие между двумя узлами BGP
**Инжектор маршрутов** - это программа, которая не участвует в физической передаче байт. Она управляет поведением роутеров в сети, отдавая им команды по BGP в виде анонсов.
**Сценарий: на одном конце роутер, на другом сервер с ExaBGP:**
	Роутер передает все маршруты серверу, как если бы тот был точно таким же роутером с настроенным BGP. ExaBGP является демоном как BIRD, BIRD на одном сервере может осуществлять BGP сессию с сервером на котором работает ExaBGP. Сервер принимает огромное количество бинарных данных с маршрутами и преобразует их в удобные `.json` файлы и отправляет их в `STDOUT` можно перенаправить стандартный вывод в БД или другое приложение, или сначала  . После получения всех маршрутов стороны друг другу шлют `KEEPALIVE`.
**Сценарий: на обоих концах стоят сервера с ExaBGP:**
	Это базовая реализация CDN или распределения нагрузки, используя имеющуюся инфраструктуру BGP. В таком случае каждый из серверов может в определенных случаях, делать определенные действия. **Например:** при перегрузке сервера А тот передает серверу Б `community` (65000:100), сервер Б примет этот `community`, сработает его скрипт ExaBGP и распознает это как знак - больше мне задачи пока не шли. 
		Таким образом, подобное общение это способ для программистов заставить сервера общаться между собой, используя имеющуюся инфраструктуру BGP. Подобные механизмы лежат в основе **оркестраторов Doker**. 
### Реализация и настройка

**Примечание(1):** Перед инициализацией ExaBGP необходимо создать конфигурационный файл. Именно следуя ему действует ExaBGP
`exabgp /etc/exabgp.conf` - запустить ExaBGP следуя выбранному файлу конфигурации
**Примечание(2):** Желательно устанавливать ExaBGP в отдельное окружение, что бы не было конфликтов библиотек на машине в будущем
`python3 -m venv /opt/[НАЗВАНИЕ_ENV]` - создать окружение
`/opt/[НАЗВАНИЕ_ENV]/bin/pip intall exabgp` - скачать ExaBGP в созданное окружение
`ip netns exec Border /opt/exabgp-env/bin/exabgp /etc/exabgp.conf` - запуск ExaBGP из изолированного контейнера **NS Border** при использовании venv. Первый путь - ExaBGP внутри окружения, второй - конфигурационный файл 

**Составление конфигурационного файла и типичные обороты:**
**Примечание(1):** ExaBGP используется STDIN и STDOUT для общения с другими приложениями. 

1. В начале конфигурации сначала всегда описывается кто такой хост и какие у него соседи а также какие маршруты передавать соседу
```
# /etc/exabgp.conf

neighbor 192.0.0.1 { # IP соседа
    # 1. Базовые настройки сессии
    router-id 192.0.0.2; # IP данного хоста
    local-address 192.0.0.2;
    local-as 65002;
    peer-as 65001;
    
    # 2. Какие семейства протоколов мы поддерживаем
    family {
        ipv4 unicast;
        ipv6 unicast;
    }
    
    # 3. Блок статических маршрутов
    static {
        # Обычный маршрут
        route 10.10.10.0/24 next-hop 192.0.0.2;
        
        # Маршрут с атрибутами (как в "настоящем" BGP)
        route 10.20.20.0/24 next-hop 192.0.0.2 as-path [ 65002 65005 ] med 100 local-preference 200;
        
        # Маршрут с BGP Community (часто используется для тегирования трафика)
        route 10.30.30.0/24 next-hop 192.0.0.2 community [ 65002:666 65002:999 ];
    }
}
```

2. Интеграция с приложениями с помощью блока `process`
```
# Описывается находясь внутри первого блокас описанием соседей

process my-python-app {
        # Команда для запуска вашего приложения
        run /usr/bin/python3 /opt/exabgp-env/my_script.py;
        
        # Формат общения (обычно JSON)
        encoder json;
        
        # Что именно ExaBGP должен пересылать в скрипт
        receive {
            parsed; # Разобранные BGP-сообщения
            update; # Маршруты, прилетевшие от соседа
            neighbor-changes; # Уведомления, если сосед упал
        }
```

### Интеграция с приложениями и программами
**Возможность управлять ExaBGP с помощью каналов `/run/exabgp.in` и `/run/exabgp.out`**:
	Можно управлять ExaBGP с помощью именованных каналов - файлы, в которые может быть записано что нужно передать демону ExaBGP, и что он отдает. Файлы будут соответственно названы: `/run/exabgp.in` и `/run/exabgp.out`. Создать их необходимо вручную. После создания и запуска демона ExaBGP можно просто записывать текст в файл .in что бы передать ввод в программу или смотреть .out что бы видеть вывод программы. Для работы с этими файлами есть красивая обертка: `exabgpcli`.

**Интеграция с HTTP (REST API)**:
	В экосистеме Python имеется большое количество готовых скриптов, которые позволяют общаться ExaBGP по HTTP. Эти скрипты помещаются в блок `process`. Скрипт поднимает локальный сервер **Flask** или **FastAPI** на порту 5000. Любое приложение или программа отправляет серверу на этот порт POST запрос с JSON в котором может быть что угодно. Даже те-же маршруты для инжектинга. Скрипт ловит запрос и пересылает его в STDOUT для ExaBGP.
